# Redis 可靠性与性能

Redis 很快，但“快”不等于“数据一定安全”。生产环境必须明确：Redis 中的数据能否丢失、缓存失效后如何恢复、Redis 故障时请求如何处理，以及单条命令是否会阻塞其他请求。

## 数据角色：缓存还是事实来源

先给数据分类：

| 数据类型             | Redis 的角色     | Redis 故障时的处理             |
| -------------------- | ---------------- | ------------------------------ |
| 用户资料缓存         | 加速读取         | 从 MySQL 重建缓存。            |
| 验证码、登录 session | 临时状态         | 让用户重新获取或登录。         |
| 文章阅读数           | 高性能计数       | 定期同步数据库，允许少量延迟。 |
| 账户余额、订单金额   | 不能作为唯一来源 | 以数据库事务和约束为准。       |
| 消息事件             | 消息传递组件     | 配置持久化、确认、重试和补偿。 |

不要因为 Redis 读写快，就把所有数据都只放在 Redis。缓存可以丢失，核心事实不能只依赖缓存。

## 缓存三大问题

### 缓存穿透

缓存穿透是指请求查询一个本来就不存在的数据：

```text
请求 id=999999
  -> Redis 没有
  -> MySQL 也没有
  -> 每次请求都打到 MySQL
```

真实场景是恶意用户不断请求随机商品 id，导致数据库被无效请求拖慢。

处理方式：

- 对 id、手机号等参数做格式和范围校验。
- 对确认不存在的结果缓存短时间空值，例如 `NULL` 或特殊标记。
- 使用布隆过滤器快速判断 id 是否可能存在。
- 对异常访问来源做限流。

空值缓存必须设置较短 TTL，避免新数据创建后仍长时间返回不存在。

### 缓存击穿

缓存击穿是某个热点 key 恰好过期，很多请求同时查询数据库：

```text
热点商品 key 过期
  -> 1000 个请求同时发现未命中
  -> 1000 个请求同时查询 MySQL
```

处理方式：

- 对热点 key 设置互斥锁，只允许一个请求重建缓存。
- 使用逻辑过期：缓存数据物理上不过期，记录业务过期时间，后台异步刷新。
- 给 TTL 增加随机值，避免多个热点 key 同时过期。

缓存击穿和分布式锁相关，但锁只负责控制“重建缓存”的并发，不负责保证业务数据正确。

### 缓存雪崩

缓存雪崩是大量 key 同时过期，或 Redis 整体不可用，导致大量请求同时访问数据库：

```text
Redis 故障
  -> 所有缓存请求失败
  -> 大量请求回源 MySQL
  -> MySQL 连接耗尽，整个服务不可用
```

处理方式：

- TTL 增加随机值，分散过期时间。
- 对热点数据预热和分批刷新。
- Redis 使用主从、哨兵或集群提高可用性。
- 应用层设置超时、熔断和降级，不能无限等待 Redis。
- 数据库连接池、线程池和回源请求设置上限。

## 缓存一致性

### 推荐的更新顺序

常见做法是：

```text
更新 MySQL
  -> 删除 Redis 缓存
```

下一次读请求发现缓存不存在，再从 MySQL 读取并重建。删除缓存通常比更新缓存简单，因为一个业务对象可能有多个缓存 key 和多个写入入口。

但这个方案仍可能存在短暂不一致。例如删除缓存失败，旧值会继续存在。因此可以补充：

- 删除失败重试。
- 使用消息队列异步删除。
- 设置合理 TTL 作为最终兜底。
- 对关键数据使用版本号或更新时间校验。

## 持久化：RDB 与 AOF

### RDB

RDB 在指定时间点生成 Redis 数据快照：

- 优点：文件小，恢复速度快。
- 缺点：两次快照之间 Redis 宕机，可能丢失最近写入的数据。
- 适合：备份、快速恢复、允许少量数据丢失的缓存场景。

### AOF

AOF 记录 Redis 执行过的写命令：

- 优点：数据通常比 RDB 更完整。
- 缺点：文件更大，恢复和重写需要更多资源。
- 适合：不能接受较多数据丢失的场景。

生产环境应根据数据重要性组合使用，并定期备份到独立存储。持久化不能替代监控、故障转移和数据恢复演练。

## Redis 故障时如何降级

缓存读取失败时，不要让所有请求无限等待 Redis：

```ts
try {
  const cached = await redis.get(key)
  if (cached) return JSON.parse(cached)
} catch (error) {
  logger.warn('Redis unavailable, fallback to database', error)
}

// Redis 不可用或缓存未命中时回源数据库
return userRepository.findOneByOrFail({ id: userId })
```

但不能对所有接口都无条件回源。高流量接口还需要：

- Redis 请求超时控制。
- 回源并发数限制。
- 熔断和短时间快速失败。
- 只返回基础数据或静态兜底数据。
- 对非核心功能暂时关闭，例如排行榜、推荐和实时统计。

## 命令性能与大 Key

Redis 命令通常很快，但 Redis 执行命令时会占用主线程。单条命令处理很大的数据，也会阻塞其他客户端。

避免或谨慎使用：

- `KEYS *`：可能遍历整个 keyspace，阻塞 Redis。
- 超大的 `HGETALL`：一次返回整个对象。
- 超大的 `SMEMBERS`：一次返回整个集合。
- 超大的 `LRANGE 0 -1`：一次返回整个列表。
- 保存几十 MB 甚至更大的单个 key：读写和删除都会产生延迟。

使用 `SCAN` 分批遍历：

```redis
SCAN 0 MATCH user:profile:* COUNT 100
```

大对象可以拆分成多个 key，列表和集合应限制长度或分页读取。监控中应关注大 key、慢命令、命令耗时和内存使用率。

## Pipeline、事务与 Lua

### Pipeline

Pipeline 将多条命令批量发送，减少客户端和 Redis 之间的网络往返：

```ts
const pipeline = redis.multi()
pipeline.get('user:name:1001')
pipeline.get('user:name:1002')
const results = await pipeline.exec()
```

Pipeline 主要解决网络往返问题，不等于业务事务，也不保证命令之间具有完整的业务原子性。

### `MULTI` / `EXEC`

Redis 事务可以将命令排队后一次执行，但它不像 MySQL 事务一样自动回滚已经执行的命令。命令执行错误时，之前的命令不会自动撤销。

因此，涉及复杂业务一致性时要明确设计补偿逻辑，不能把 Redis `MULTI` / `EXEC` 当成 MySQL 事务的替代品。

### Lua

Lua 适合把“读取、判断、修改”组合成一次原子操作，例如限流和安全释放分布式锁：

```lua
local count = redis.call('incr', KEYS[1])
if count == 1 then
  redis.call('expire', KEYS[1], ARGV[1])
end
return count
```

脚本执行期间不会被其他 Redis 命令插入，但脚本本身不能写得过重，否则同样会阻塞 Redis。

## 分布式锁的可靠性边界

Redis 锁适合短时间、可重试、需要跨进程协调的操作，例如同一订单的重复处理、定时任务抢占和缓存重建。

它不适合单独承担以下职责：

- 保证账户余额永远正确。
- 替代数据库唯一索引。
- 保护一个可能执行数分钟的长任务。
- 在 Redis 网络分区时提供绝对一致的锁语义。

安全释放锁的核心是“校验 token 后删除”：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

锁的正确性还依赖 TTL、续期、重试策略和业务幂等设计。最可靠的做法是：Redis 锁减少并发，数据库事务和唯一约束保证最终正确，业务接口支持重复调用。

## 监控指标

建议监控：

- 内存使用量和淘汰 key 数量。
- 命中率、缓存未命中率。
- 慢命令和命令执行耗时。
- 大 key 数量和 key 数量增长速度。
- 连接数、阻塞客户端数和拒绝连接数。
- RDB/AOF 持久化耗时与失败次数。
- 主从复制延迟、哨兵状态或集群节点状态。

## 小结

- Redis 的可靠性首先取决于数据角色：缓存可以重建，核心事实不能只依赖 Redis。
- 缓存要处理穿透、击穿、雪崩和短暂不一致。
- 使用 TTL、RDB/AOF、监控、故障转移和降级方案提高可靠性。
- 避免 `KEYS` 和超大 key，使用 `SCAN`、分页、拆分 key 和 Pipeline。
- Redis 锁负责协调并发，数据库事务、唯一约束和幂等设计负责最终正确性。
